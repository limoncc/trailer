# Trailer 日常工作流

开源后代码管理采用 **GitHub Flow** —— 最简单且完全够用，避免过度工程。

## 分支策略

```
main（始终可发布、稳定）
  └─ 日常不直接推半成品

新功能 / 修复 → 开分支 → 开发 + 验证 → PR 合并回 main → 打 tag 发布
```

**分支命名约定**：

| 分支 | 用途 |
|---|---|
| `feat/xxx` | 新功能（如 `feat/report-toc`）|
| `fix/xxx` | 修复（如 `fix/markdown-breaks`）|
| `docs/xxx` | 文档（如 `docs/readme-screenshots`）|
| `chore/xxx` | 构建 / CI 杂项 |

## 日常工作流

```bash
# 1. 从最新的 main 开功能分支
git checkout main && git pull
git checkout -b feat/xxx

# 2. 开发、提交（小步，按功能）
git add ... && git commit -m "feat: ..."

# 3. 推分支 + 开 PR
git push origin feat/xxx
gh pr create --fill

# 4. 合并回 main（用 PR 而非直接 push，保留记录）
gh pr merge --squash
```

## 发布（保持现有 tag 机制）

```
main 稳定后 → git tag v0.1.x → push → CI 自动构建 GitHub Release → 手动 PyPI
```

**main 永远可以随时打 tag 发布** —— 这是核心原则。

## 与现有 CI 配合

- push 到 `main` 的 `docs/**` 变更 → 自动部署文档站（deploy-docs.yml）
- 打 `v*` tag → 自动构建 GitHub Release（release.yml）
- 功能分支推到远端**不会**触发 release（只有 tag 触发）——安全

## 可选增强（按需）

1. **main 分支保护**（Settings → Branches）：禁止直接 push main，必须走 PR
2. **PR 模板**（`.github/PULL_REQUEST_TEMPLATE.md`）：规范 PR 描述
3. **release 分支**（如 `release/v0.2`）：只有需要同时维护多个版本时才值得

## 要点

对单人项目关键就两条：**功能分支开发** + **main 保持可发布**。PR 即使是自己也可以开（squash 合并让历史干净），还能触发 CI 检查。
